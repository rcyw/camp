# 双通道执行：代码审查与修复

本次审查针对 [双事项有界并行](./bounded-pair-execution.md)，并检查它与已有串行 Worker、不可变结果补交、版本历史和部署方式的交界。保留三种显式计划模式及已有协议，不扩展任意依赖图或跨主机执行。

## 发现与处理

| 边界 | 原问题与影响 | 修复约束 |
| --- | --- | --- |
| 串行与池切换 | 池进程被强杀后内核锁释放，但旧容器仍活着；另一个身份及 home 的串行 Worker 可以继续领取 | 先恢复自身已登记事实，再检查全 daemon 的托管容器。存在未清理资源时零新领取，保留其他身份的资源并要求恢复原 manager |
| 双通道资源观察 | Docker 容器快照在等待期间过时，另一条 lane 已释放 reservation，合法旧资源会被误判为未知资源，导致整个池误停 | 将快照与 reservation 的同一 generation 对齐；创建前再次核对当前归属，真实未知资源仍拒绝 |
| 旧结果与新配置 | 启动时先验证新的 CPU、内存或 PID 配置，配置改变或无效会阻止旧 outbox 和沙箱恢复 | 使用原持久身份恢复既有日志及原样结果；恢复后再验证新执行配置，禁止用新的资源配置覆盖原池声明 |
| 恢复协议探测 | 旧服务可能忽略未知的 `restoreOnly` 字段，把未绑定 intent 的恢复查询当作新领取 | 有 pending intent 时先只读确认协议 4 的非分配契约；不支持时只恢复已登记的事实并保留 intent，不发送可能分配的请求 |
| 资源协议 | 每容器允许 64 CPU，但四容器的池声明只允许 128 CPU，总量合法配置无法使用 | 协议上限与四容器最坏总量对齐，先严格校验再保存新池身份 |
| 旧协议选择 | 通用兼容检查可为未冻结的 legacy 任务选择协议 4，却没有对应的资源池要求 | 未冻结 legacy 的选择与控制侧一致，限定已实现的 1/2；显式历史协商仍按原快照恢复 |
| 旧任务完成合同 | legacy 协议 2 没有要求 Diff 能力，完成时却被串行交付的强制 Diff 门禁拒绝 | 强制 Diff 限于串行交付合同；legacy 保留原冻结要求，现代 Worker 仍可报告 Diff |
| 容量等待 | 已确认兼容的任务因 lane、角色或物理容量忙碌而暂不能领取时，后续轮询把兼容信息清空 | 保留兼容的任务要求，返回明确的等待原因；其他任务的不兼容不覆盖已知兼容的等待 |
| 执行与版本界面 | 展开历史仍截断长摘要；独立事项完成不更新公共候选，已打开的历史面板不会刷新 | 历史展示完整摘要；按逐事项不可变候选与里程碑刷新，同时保留人工版本选择，稳定轮询不打断检查 |
| 成果捕获 | 整体验证后的合法返工可能生成新候选，捕获脚本却仍将最初的集成候选当成交付成果 | 按最终清单和完整候选身份选择对应生产记录，分别记录集成候选和交付候选，历史成果不要求仍是最新 Room head |
| 验收进程 | 部分探针未转发父进程停止信号，可能留下 Worker；凭据断言失败可能打印令牌 | 子进程由创建它的探针负责停止并等待退出；敏感比较使用不暴露凭据的断言 |

以上问题通过针对旧行为的回归测试复现后修复。新的部署示例为
[camp-worker-pool.service.example](../../deploy/camp-worker-pool.service.example)，沿用私有配置、稳定 home 和宿主 manager 互斥规则。

## 验证边界

自动化检查覆盖协议与插件、服务端与真实 PostgreSQL、Runtime、Web DOM，以及验收进程和成果选择。真实基础设施验收使用合成角色输出，通过实际 HTTP、PostgreSQL、Docker 和 LayerFS 验证双构建、逆序完成、可信合并、取消和 SIGKILL。

增强的崩溃场景先保留两个实际孤儿沙箱，再确认另一身份的串行 Worker 在零领取时被拒绝且不删除它们；原池即使收到无效新配置，也必须先完成原日志恢复和清理，恢复有效配置后才重新开放领取。该过程不调用模型。既有真实 DSH 的 178 秒自主交付证据仍单独保存在 `.camp/parallel-model-latest.json`。

本次不修改已应用的 0376–0383 迁移，也不删除既有 Room、已接受候选或历史结果。仍只支持同内核的本地 LayerFS Disposable Store；进程恢复验证不能替代掉电恢复、备份或跨主机存储传递验证。
