# 单 Room 自主交付

本阶段将固定的三角色流水线改为协调者提交计划、平台调度执行的完整需求闭环。只使用一个项目、三个 DSH 角色和串行开发。现有 LayerFS 候选、执行日志、租约、预算及取消机制继续复用。

下方实施记录属于协议 1 的串行交付验收。当前新目标默认使用协议 2，须先配置项目检查，并在最终审查前通过独立系统验证；当前新增能力与本轮验收状态见 [候选 Diff 与可信验证](./delivery-evidence.md)。历史目标继续使用创建时冻结的约定。

## 用户流程

1. 用户在频道或团队执行面板提交需求和验收目标。
2. 协调者检查项目，通过 `camp_submit_plan` 提交有界、有序的结构化任务清单。每项包含目标、说明、验收条件和验证方式。
3. 服务端持久化计划，Worker 为开发角色自动领取当前任务。通过审查后才推进下一项；后项使用前项通过审查的候选版本。
4. 开发提交结果后自动创建独立审查。驳回时只返工当前项，保留先前任务和全部尝试历史。
5. 阻塞问题关联任务和接收角色。当前执行保存候选后挂起，释放 Worker；协调者处理问题，需要用户决策时在界面请求回复。回复后重新领取任务，恢复原候选和上下文。进度事件不触发角色唤醒。
6. 全部任务通过后，新 v2 目标先运行冻结的项目检查；失败按预算进行目标范围修复并重验。检查通过后，审查者针对原始需求执行整体验收。通过后由协调者汇总结果、验证证据、遗留事项和最终候选。既有 v1 目标保持原来的审查顺序。
7. 成功结算后，Room 保存已接受候选。下一需求继承该版本；界面也提供基于已完成成果继续的入口。成果可通过鉴权清单和本机导出工具取用。

## 一致性边界

- 一个 Room 同时推进一个串行目标。计划每次人工 attempt 只接受一份；完全相同的重放返回相同任务，不同内容返回冲突。
- 任务领取和生命周期属于可信 Worker，模型工具只提出计划、汇报、问题及审查结论。
- 每次执行明确绑定一个输入候选。多父输入和无法确定的版本不能自动选择最后一个作为回退。
- 候选以 `refKind` 和 `refId` 标识不可变版本：初次导入的 Layer 与执行后产生的 Commit 分开表达。未修改文件时可以审查和交付原 Layer，不创建隐藏标记来伪造 Commit。
- 审查结论绑定实际检查的候选。规划、澄清、总结及审查不能修改被接受的项目文件。
- 最终结果通过服务端检查后才推进 Room 的已接受版本；过期执行、旧 attempt、取消目标和已变化的基线不能覆盖它。
- 问答有持久身份、接收角色和待处理状态。挂起、回答及恢复可重放；已回答或已取消的问题不重复唤醒角色。
- 所有执行、返工、澄清和最终验收都消耗目标预算。失败和预算耗尽保持可检查，不默认标为成功。
- 导出使用可信候选身份，输出到新的外部位置，不覆盖原项目目录。LayerFS 仍采用本机 Disposable Store；文件候选不等同于进程恢复或跨主机持久存储。

## 验收

以一个真实的小型项目完成至少三个有序任务，覆盖自动审查驳回和返工，并提交第二个需求验证成果继承。除需求澄清外，不需要人手工分派、催审或转述审查意见。

分别记录协议测试、真实 PostgreSQL 并发与迁移、真实 Docker/LayerFS 导出、浏览器交互和真实 DSH 模型执行。界面应能回答：任务是什么、谁在处理、卡在哪里、审查要求什么、最终交付哪个版本。记录人工回复次数与原因、自动审查和返工次数，以便评估协调负担。

并行开发、多父候选合并、任意依赖图、逐行归因等完整历史浏览和跨主机 Worker 留在后续阶段；单父候选链使本阶段可以独立验证。当前已提供生产候选的版本列表及累计文件 Diff，不等同于完整 Git 历史工具。

## 接口与状态

新需求默认 `workflow: "serial"`，先建立一个协调规划任务。显式单角色探针和指定 `workflow: "legacy"` 的请求保留旧流程。串行请求不接受任意 `dependsOn`、角色或模型分配。协调计划每个 attempt 只接受 revision 1，同内容重放幂等，不同内容冲突。

```json
{
  "planRevision": 1,
  "summary": "实现搜索，再接入接口与页面",
  "tasks": [
    {
      "key": "search",
      "title": "实现搜索",
      "description": "扩展现有搜索函数，不修改输入数组",
      "acceptance": "支持大小写不敏感的名称过滤和排序",
      "verification": "运行搜索单元测试并覆盖空结果"
    }
  ]
}
```

模型任务类型是 `plan`、`build`、`review`、`final_review`、`summary` 和 `clarification`。v2 的 `verification` 是没有模型角色、Agent 身份或 canonical task 的系统 operation，复用同一 Run 账本。每项独立审查通过后才创建下一项的开发任务。整体验收驳回会建立目标范围的修复任务，v2 须重新验证后再整体验收，不把整体验收意见错误归给某个已经通过的子任务。

| 调用方 | 接口 | 行为 |
| --- | --- | --- |
| 频道成员 | `POST /api/camp/rooms/:roomId/tasks` | 提交需求；可带预算及当前已接受目标的 `fromGoalId` |
| 频道成员 | `POST /api/camp/rooms/:roomId/questions/:questionId/answer` | 回答正在等待人工决策的问题，重复同一答案不重复恢复 |
| 频道成员 | `GET /api/camp/rooms/:roomId/goals/:goalId/result` | 下载不含凭据的结果清单；未完成时 `resultReady: false` |
| 当前规划 Run | `POST /api/camp/worker/runs/:runId/plan` | 持久化计划，不能直接领取或完成任务 |
| 当前执行 Run | `POST /api/camp/worker/runs/:runId/questions` | 创建持久阻塞问题；返回 `requiresSuspension` |
| 澄清 Run | `POST /api/camp/worker/runs/:runId/questions/:questionId/answer` | 记录角色答案，澄清执行结算后恢复原任务 |
| 澄清 Run | `POST /api/camp/worker/runs/:runId/questions/:questionId/escalate` | 请求人工决策；澄清执行结束后才允许人回复 |
| 最终总结 Run | `POST /api/camp/worker/runs/:runId/finalize` | 记录总结、证据和遗留事项，自动绑定最终候选 |
| 可信 Worker | 原 Claim / Heartbeat / Complete / Reconcile / Cleanup | 管理执行权、文件候选、可靠结算与清理 |
| 可信 Worker | `GET /api/camp/worker/goals/:goalId/result` | 读取当前凭据所绑定 Room 的成果清单 |

插件工具请求附带 `workerId`、`runId` 和 `epoch`；服务端校验它们与 URL、当前执行所有者及 Run 能力一致。计划 item 严格拒绝未知字段，避免把提交的依赖图静默当成有序列表。

问题工具不自行转移租约。Worker 在执行期间检查持久问题状态；需要让出时停止 DSH，确认本次容器中的 Agent 工具进程停止，再保存候选、清理执行资源，并通过原来的持久 outbox 提交 `status: "suspended"` 和 `questionId`。原任务进入 `waiting_question`，澄清任务不依赖它完成，避免唯一 Worker 自锁。问题已持久但尚未挂起时发生崩溃，新的执行 epoch 会接管问题的活动执行身份，历史来源保留。

角色答案和人工升级均持久化。只有澄清执行完成后，原任务才可重新排队；升级后的人类回复同样受此限制。取消、预算耗尽、旧 attempt、跨 Room 与已撤销权限不能回答或重新唤醒旧任务。普通进度不进入问题收件箱，也不计作人工协调。

## 文件身份与成果取用

候选包含 `type: "layerfs"`、`projectId`、`refKind`、`refId`、`rootId` 和固定 `imageId`。Commit 引用为 `12…`，并带同值的 `commitId`；初始 Layer 引用为 `32…`，带 `layerId`。两者都是不可变文件版本，不能把 Layer 的 ID 填进 Commit 别名。每次执行记录确切输入候选和输出候选，审查绑定实际挂载的版本，非开发任务的文件根必须保持不变。

`camp_finalize` 只持久化总结。可信 Worker 结算总结任务时，服务端核对最终审查版本和 Room 基线 revision，再原子推进 `acceptedHead`。同一完成结果重放不会再次推进。下一需求默认继承这个版本；旧目标的基线已经过时后，不能重试覆盖新成果。

清单由鉴权 API 下载，包含候选身份、总结、证据、遗留事项和协调指标，不包含 Store 路径或 Worker/模型凭据。在保存同一 `CAMP_RUNTIME_HOME` 和 Docker Store 的主机上导出：

```sh
node packages/camp-runtime/scripts/export.mjs \
  --manifest ./camp-result-GOAL_ID.json --output /tmp/camp-result-GOAL_ID
```

也可使用 `--archive /tmp/camp-result-GOAL_ID.tar`。输出必须是新的外部路径，既有目标和源目录覆盖会被拒绝。本地清单是用户提供的输入，CLI 会在对应 Room 的本机 Store 中再次验证引用和文件根；它不声称清单文件具有数字签名。输出为完整快照，删除的文件不会在新目录中残留。导出保持普通权限和安全相对符号链接，拒绝越界路径、绝对外部链接与特殊文件。

界面的人工回复次数、角色回答次数、返工次数和人工重试次数来自持久记录。它们用于评估协调负担，不能代替对真实业务需求质量的判断。
