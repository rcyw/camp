# Camp 架构边界与演进审查

本记录区分可以长期保留的职责边界、当前单机实现的限制，以及扩展前必须补齐的工作。功能范围与接口见 [单 Room 自主交付](./serial-room-workflow.md) 和 [候选 Diff 与可信验证](./delivery-evidence.md)；同基线合并见 [可信候选集成](./trusted-integration.md)，双通道执行见 [有界并行](./bounded-pair-execution.md)，协议 5 的节点依赖和多次可信集成见[有界依赖图](./bounded-dag.md)，私有制品与单写入权威交接见[传输契约](./private-artifact-transfer.md)。

## 仓库约定

本轮核对了根目录、隐藏配置目录及父目录中的规则文件。Camp 当前没有根级 `AGENTS.md`，存在 [CLI 设计规则](../../packages/cli/AGENTS.md) 和根级 [贡献说明](../../CONTRIBUTING.md)。CLI 规则直接约束 `packages/cli`；本阶段未修改该目录。[Agent 产品说明](../../manual/agent-knowledge/agent.md) 描述上游参与者与权限语义，不是仓库级编码指令。

CLI 规则中的单一事实源、明确查询与变更、生命周期由 daemon 管理、不提供阻塞等待的原则，也适用于 Camp 的边界。DSH 插件只暴露本轮角色的计划、问题、汇报和审查操作，不持有通用 Agent 凭据。工具使用角色名，不要求模型选择 Agent 身份 UUID；问题 ID 是非身份资源锚点。平台领取、租约、进程和资源管理由可信 Worker 执行。

## 长期保留的边界

| 层 | 保存的事实与责任 | 边界 |
| --- | --- | --- |
| Camp 控制侧 | Goal、计划、任务、Run、问题、预算、审查、已接受版本 | PostgreSQL 中的持久状态决定推进；聊天和界面展示这些事实 |
| DSH ACP 与插件 | 当前角色的推理、项目操作、计划建议与证据 | 短期 Run 能力，不领取其他任务、不扩展角色或预算 |
| 可信 Worker | 领取、续租、停止进程、候选与 outbox、资源清理 | 执行权与物理清理分别记录；不靠模型承诺结束执行 |
| Sandbox 适配器 | 一次执行的隔离环境及工具进程 | 可替换部署方式；基础设施与模型真实凭据不进入项目文件 |
| LayerFS 适配器 | 不可变文件引用、执行分支、快照及导出 | 文件版本不等于进程、数据库或外部服务状态 |

这些边界允许保留当前状态机，再替换执行位置或存储实现。协调者提交计划，服务端校验和调度；角色之间通过持久问题交接，普通聊天不驱动无限唤醒。任务返工、整体验收返工和最终接受是不同的状态转换。

角色的频道身份长存，一次 DSH Run 则是短期执行实例。保留 Raft 的参与者、消息归属和权限语义，不把 Agent 的逻辑身份绑定到某个容器或常驻模型进程；恢复时新建执行实例，沿用持久任务和候选上下文。

候选以 `refKind/refId/rootId` 表示明确的不可变文件身份。初始 Layer 和执行后的 Commit 都是合法引用，不用伪造空提交满足接口。审查绑定检查过的候选，总结结算才原子推进 Room head；下次需求继承该版本。

独立验证是无模型角色的系统 operation，复用同一 Run 账本、租约和恢复链路。管理员配置的检查策略在目标创建时冻结；平台验证精确候选与镜像并生成回执，最终审查和成果结算都必须经过门禁。每项检查使用候选的全新普通容器副本，外部固定 harness 按内容摘要只读挂载，开发不能通过修改项目测试替代这部分验收。

## 规范任务的唯一写入责任

Camp 复用 Raft 的任务记录和权限服务，但 Camp 绑定任务必须由 Camp 生命周期管理。普通任务面板不能在旁路领取、改派、修改执行语义或删除这些任务；读取和正常评论不需要取得调度权。可信 Camp 操作通过内部、限定任务范围的授权调用原任务服务，在同一事务中更新规范任务与 Camp 状态。

这一约束放在任务服务的变更边界，覆盖单项与批量领取、改派、状态变更、修改说明、资源回执和删除。内部授权限定一个 Room 和任务，必须处于生命周期事务中；退出作用域即失效，不能通过 HTTP 参数取得。续租与提交还会核对规范任务的负责人、状态和当前角色成员资格，异常变更会停止执行，清理不覆盖已变化的规范记录。

Camp 任务与绑定在同一事务中创建并公开，没有把既有普通任务附加为 Camp 任务的入口。普通任务沿用原来的并发与锁顺序；Camp 按 Room、频道 conversion fence、有效频道行、排序后的角色身份、规范任务的顺序进入生命周期操作，包含领取前的过期执行扫描，避免与 Agent 删除反向持锁。频道删除先锁频道再关闭规范任务，本地普通频道的成员移除先锁频道再删除成员，避免私有频道自动关闭或可见性切换引入反向锁。角色成员关系在执行事务内受锁保护，Room 凭据不能绕过撤权。频道生命周期已关闭规范任务时，Camp 幂等同步自己的终态，避免重复关闭阻断清理。

## 当前明确的实现限制

- 一个 Room 同时推进一个目标，保留三个固定逻辑角色。默认按有序清单执行；显式 `parallel_pair` 由同一个开发角色并行执行两个独立事项，共享不可变基线，逐项审查后可信集成。两条本机 lane 由一个可信 supervisor 管理，审查角色仍单实例。显式 `bounded_dag` 使用协议 5 与计划 revision 2，最多六节点、双父输入和两个最终节点；每项获批后解锁依赖，多父必须保留全部来源并解析血缘或先可信集成。任意规模图和存在歧义的原生祖先仍不支持。
- Runtime 当前直接实现 Linux、Docker 与本地 LayerFS Store。HK 与 MY 两台真实主机已验证私有制品冷交接、全历史恢复和单写入权威切换；它仍不是通用 Sandbox 平台，也不支持两个主机并发写同一 Room Store。
- LayerFS 使用同内核、本机 Disposable Store。Worker journal 的持久写入不能替代 Store 自身的掉电恢复和跨主机制品持久化验证。
- Worker 停止 ACP 后还要停止本次容器中的 Agent 后台进程，再取快照。已提供 API 离线时的显式本地回收，按私有 journal 和同一 Worker 内核锁核对归属，不改原 outbox；CPU/内存/PID 限制在 Agent 启动前核验。无人值守离线回收、磁盘硬配额与 egress 策略仍未实现。
- Worker 在新领取前协商协议版本、任务类型、快照引用与固定 harness 能力，Run 固定实际协商快照。协议 1 保留原目标语义，协议 2 要求开发 Diff 与独立验证，协议 3 增加同基线双候选可信集成，协议 4 增加固定存储域和双 lane 池，协议 5 增加有界依赖图和可重复的节点/成果集成。跨主机与旧新服务端混跑的发布流程尚未验证。见 [Worker 协议](./worker-protocol.md)。
- 角色工具 Schema、服务端与 Runtime 核心校验、Web 域类型已收敛到轻量共享协议包，类型从同一来源生成。服务端权限与事务、Runtime 文件策略和浏览器投影仍由各层负责。
- 当前 Room 界面轮询快照，适合这一轮单 Room 验证。长期连续使用需要分页和增量事件投影，避免历史目标越来越多时重复查询全部数据。

## 后续收敛顺序

1. 验证单 Room 自主交付，记录人工回复、人工重试、返工和成果质量，不用消息数量代替协作效果。
2. 已提取轻量共享协议定义与验证器，并增加 Worker 在领取前的能力协商；继续保留 ACP 和专用 Run 能力边界。
3. 候选 Diff 与独立验证、固定工具链、首次连接预检和单机离线回收已实现，见 [部署与恢复](./single-host-worker.md)。同基线两项任务的可信候选集成已实现，并验证冲突、精确 outbox 恢复与未知原生结局停止，见 [可信集成](./trusted-integration.md)。同存储主机的双 lane 有界并发已经启用，见 [执行池](./bounded-pair-execution.md)。
4. 候选 Store 冷备份、独立恢复和显式存储迁移已实现，见[存储生命周期](./storage-lifecycle.md)。已验证同一主机上的新目录、新 volume 与新池继续交付，以及两台真实主机上的私有传输、实际断网续传、全历史恢复和旧池 fencing，见[两机验收](./two-host-worker.md)。跨主机总资源调度、并发写入和掉电恢复仍是独立验收门禁。
5. 协议 5 有界任务图已增加持久依赖、获批输入、多次可信集成及局部返工，见[图契约](./bounded-dag.md)。
6. 已增加[稳定 HTTPS、常驻 Worker 与凭据续租](./https-control-plane.md)，以及[私有 OCI 分发](./private-oci.md)。DSH 的真实模型验收与基础设施的 synthetic 验收分别记录。并行远端执行仍需要显式制品来源到新权威候选的映射或受支持的 LayerFS graph import，不能拼接两个独立写入的 SQLite Store。

本阶段可以作为上述演进的基础。已验证的冷 Store 交接不代表运行中进程迁移、掉电恢复、多租户资源隔离或任意并行合并能力。
